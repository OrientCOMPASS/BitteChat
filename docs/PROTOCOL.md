# BitteChat 协议规范 (v1.2)

**一个种子 = 一个群聊**：任何现有的 BitTorrent 种子（v1 infohash）天然就是一个聊天室，
无需"创建"群组；消息以 git 式哈希链 DAG 组织，经 BEP44 DHT 与 BEP10 自定义扩展消息传播。

> v1.2（应用 v0.6.0）变更：**私聊（DM）不再使用清单种子**——改为在共享房间的
> swarm 连接上定向发送签名的 请求/接受 帧建立，消息仅两台设备间直连传输、仅本地
> 存储（不写 DHT、不新建种子）；`bc_chat` 扩展握手携带节点身份公钥（`bc_pk`），
> 支持定向投递与在线状态；**群名改为纯本地备注**（不再广播 rename 系统消息）；
> **头像不再有任何广播途径**（v1.1 中仅存于 DM 清单，随清单机制一并移除）。
>
> v1.1（应用 v0.5.0）变更：普通群聊不再使用"清单种子"（manifest torrent）。
> 房间 ID 即内容种子的 infohash，头指针签名密钥由 infohash 确定性派生。

## 1. 群组（种子即群聊）

### 1.1 房间标识

**每个 v1 种子对应一个聊天室**，不存在独立的"建群"动作：

```
gid   = 种子的 v1 infohash（20B）
salt  = "bc1:" + hex(gid)
名称   = 种子名（元数据可用前显示 dn / 短哈希占位；用户可本地改名并广播 §5.2）
```

- **入群 = 添加种子**：客户端接受磁力链、裸 40 位十六进制 infohash、32 位 base32
  infohash 或 .torrent 文件；添加后该任务的 swarm 即聊天室成员集合。
- **邀请 = 分享种子**：把磁力链 / infohash 发给别人即可，对方添加同一种子就进入同一房间。
- 聊天不要求下载内容本身：仅凭 infohash（磁力）即可参与 DHT 同步与 swarm 聊天，
  内容下载与否是独立的用户选择。
- 对普通 BT 客户端而言这只是又一个 peer；`bc_chat` 扩展只在两个 BitteChat
  客户端之间生效（§3.2）。

### 1.2 头指针密钥（确定性派生）

房间没有清单文件可交换密钥——头指针签名密钥由 infohash **确定性派生**，
任何客户端都能独立得到同一密钥对：

```
head_seed = SHA-256("bitte-chat-torrent-head-v1" || infohash)
head_pk   = ed25519(head_seed).public
```

与 v1.0 清单中的 `head.s` 一样，这是"共享写权限"密钥：安全性不依赖其保密
（知道 infohash 即可推导），而依赖消息级签名与 DAG 合并（§4）。头指针仅是
加速器/提示，不是真相源。

### 1.3 头指针 (BEP44 mutable item)

```
pk    = head_pk（§1.2 派生）
salt  = "bc1:" + hex(gid)
value = { "h": [<20B 消息ID>, ... ≤16], "t": <unix毫秒>, "v": 1 }
seq   = 单调递增
sig   = ed25519(bencode({"seq": seq, "v": value}) + salt)   # BEP44 标准
```

### 1.4 DM 频道（v1.2：纯本地，无清单种子）

端到端加密私聊频道**没有任何种子/清单/DHT 条目**，只是双方设备上的一份本地状态：

```
gid    = sha1(min(kA,kB) || max(kA,kB) || "bc-dm-1")   # 与 v1.0/1.1 相同，历史频道可延续
双方    = {k: ed25519 公钥, x: X25519 公钥} ×2          # x 从对方在共享房间的消息（§2.1 的 x 字段）
                                                        # 或握手帧中习得，双方各自本地保存
名称    = 对方昵称（本地展示用）
```

建立流程（请求/接受，全部经共享房间 swarm 的定向 `bc_chat` 帧，§3.2）：

1. 发起方对目标公钥定向发送 **DmReq**（携带发起方 `pk`、昵称、`x`、时间戳，
   ed25519 签名覆盖全部字段）；
2. 接收方 UI 弹出同意框（**同意前不落盘任何频道状态**）；接受则回复签名的
   **DmAccept**（携带自己的 `x`），双方各自合成上述本地频道；婉拒回复 **DmReject**；
3. `gid` 由双方公钥确定性派生，接收方必须校验 `gid == dm_gid(己方pk, 对方pk)`，
   防止第三方伪造频道 ID。

v1.0/v1.1 的清单 DM 频道（含 `dm_invite` 系统消息邀请）已废弃：旧频道本地历史保留、
可继续经 v1.2 传输层通信（双方 gid/密钥推导一致），但其清单种子不再重新加入会话。

## 2. 消息

### 2.1 编码与签名

消息是规范 bencode 字典（键按字节序排序、整数最短表示、无空白——与 libtorrent `bencode()` 输出字节一致）：

```
{
  "v":   1                          # 协议版本
  "g":   <20B gid>
  "p":   [<20B 父消息ID>, ... ≤8]    # DAG 父链接（genesis 为空表）
  "s":   <int64 作者序号>            # 每作者每群单调递增
  "t":   <int64 unix 毫秒>
  "k":   <32B 作者 ed25519 公钥>
  "n":   <UTF-8 作者昵称 ≤64B>
  "y":   <int 类型>                  # 1=文本 2=附件 3=系统 5=分块
  "b":   <载荷 bytes>
  "sig": <64B ed25519 签名>          # 对不含 sig 键的规范编码签名
}
```

- **消息 ID** = `SHA-1(完整规范编码字节)`（含 sig）。
- 整条编码 **≤ 950 字节**（BEP44 不可变条目 1000B 限制内）。
- 验证规则：严格 bencode 解码 → 重编码字节必须与原文一致（拒绝非规范编码）→ 验签 → 时间戳在 `(-∞, now+24h]` → 父链接 ≤8 且无自引用 → 时间戳不得早于已知父消息 10 分钟以上。

### 2.2 载荷类型

| y | 载荷 b |
|---|--------|
| 1 文本 | 原始 UTF-8 字节（≤600B） |
| 2 附件 | `{"ih": <20B 附件种子 infohash>, "name": ..., "size": int, "mime": 可选}` |
| 3 系统 | `{"st": "create"|"join"|"leave", "d": 详情}` |
| 5 分块 | `{"cid": <8B 随机>, "ci": 序号 1..n, "cn": n, "d": <文本片段>}` |

长文本自动拆分为分块链：第 1..n 块依次以父链接相连，展示层按 `cid` 重组。

### 2.3 附件

附件即普通 BT 下载：发送方对文件做种（v1、无 tracker、DHT 发现），消息携带 infohash；接收方以 `magnet:?xt=urn:btih:<ih>` 下载。**附件对全网可见**（知道磁力链的任何人都能下载），群消息只是分发链接。

## 3. 存储与传播

### 3.1 DHT（离线可达，BEP44）

- **消息本体** → 不可变条目，target = 消息 ID（内容寻址，即 git object 模型）。
- **头指针** → 可变条目（§1.2），指向当前 DAG 头集合。

### 3.2 `bc_chat` 扩展消息（在线直推，BEP10）

在房间种子的 swarm 内，peer 通过扩展握手互相通告：

```
m: { "bc_chat": 42, ... }      # 42 为本端分配的扩展消息 ID
bc_cap: 1
bc_pk: <64 hex 字符>           # v1.2：本节点当前身份的 ed25519 公钥（可选，
                               # 旧客户端没有；用于定向投递与在线状态）
```

消息体为 bencode 字典（经 `[u32 长度][0x14][对端扩展ID][payload]` 帧发送）。
m:1-4 在房间内广播；m:5-10 为 v1.2 DM 帧，**只发给握手中 `bc_pk` 匹配的单个
peer**（定向投递；发送方所在连接以外无人收到）：

| m | 含义 | 字段 |
|---|------|------|
| 1 | 头通告（连接时/新消息后） | `h`: [消息ID...] |
| 2 | 消息直推 | `msg`: <消息原始字节> |
| 3 | 请求缺失消息 | `w`: [消息ID...] |
| 4 | 消息应答（≤8条/帧） | `b`: [<消息原始字节>...] |
| 5 | DM 请求 | `g`: gid, `p`: 发起方pk, `n`: 昵称, `x`: X25519公钥, `t`: ts, `s`: ed25519签名(m5‖g‖p‖n‖x‖t) |
| 6 | DM 接受 | `g`, `x`, `t`, `s`: 签名(m6‖g‖x‖t) |
| 7 | DM 消息 | `g`, `msg`: <密封消息原始字节> |
| 8 | DM 送达回执 | `g`, `i`: 消息ID, `s`: 接收方签名(m8‖g‖i) |
| 9 | DM 婉拒 | `g` |
| 10 | DM 补发请求 | `g`, `q`: 请求对方作者序号 > q 的消息 |

收到 m:2/m:4/m:7 后仍需完整验证（§2.1）；房间新消息会向其他 peer 转发一跳
（gossip），以最近 4096 个 ID 的去重集防止风暴。DM 帧**从不转发**。

在线状态 = 当前持有 `bc_chat` 连接（完成扩展握手）的 peer；`bc_pk` 使在线状态
可以按"人"（身份公钥）而不是按连接聚合。为保住聊天通道，客户端关闭
libtorrent 的 `close_redundant_connections`（做种端↔做种端连接不因"无块可换"
被断开）。

### 3.3 同步流程

```
进入房间: 磁力/infohash/.torrent → 添加为普通 BT 任务 → gid=infohash 注册房间
          （DM: 磁力 → 下载清单种子 → 解析 manifest → 注册频道）
拉取:   get mutable(pk, salt) → 验签 → 对未知头 get immutable(id)
        → 验证/入库 → 对新出现的缺失父链接继续 BFS 拉取（并发 ≤8，
        失败指数退避 15s→5min）
收敛:   本地头集合变化 → put mutable(seq = max(已知)+1) 合并发布
        + ext 广播 m:1
发送:   新消息(父=当前头) → 本地入库(state=pending) → put immutable
        + ext 直推 m:2 → 发布新头；put 确认回执后 state=confirmed，
        失败进 outbox 指数退避重试
轮询:   前台群 15s / 后台群 90s 重新拉取头指针（ext 直推可达时几乎无延迟）
```

## 4. 安全模型

- **完整性**：每条消息独立签名（作者 Ed25519 公钥随消息携带）。篡改任何一个字节 → 验签失败/ID 不符 → 丢弃。
- **历史序**：消息通过 `p` 引用父消息 ID，形成哈希链 DAG。删除或改写已扩散的历史需要重签所有后续消息——不可能。
- **并发与合并**：多作者并发发言产生多头；任何新消息引用全部已知头即完成合并（同 git merge）。全局展示序 = 拓扑序 +（时间戳、作者序号、ID）确定性排序，所有节点计算结果一致。
- **头指针回滚攻击**：持有群密钥的恶意成员可以发布旧头（更高 seq）。诚实成员本地 DAG 包含真实历史，下一次发布即把旧头合并回来；不可变消息条目本身无法被覆盖或删除。头指针仅是**加速器/提示**，不是真相源。
- **垃圾消息**：无准入控制（磁力链即能力）。缓解：消息 950B 上限、DHT 条目天然限速、UI 可按作者过滤。抗 Sybil 不在 v1 范围。
- **隐私**：内容不做端到端加密（群内广播模型，任何持邀请者可读）；传输层为 BT 协议加密（MSE/RC4）+ 可选 uTP。IP 暴露面与普通 BT 客户端相同（swarm 成员互见）。

## 5. 与其它客户端的兼容性

- 房间/附件种子为标准 v1 种子（`v1_only`）；peer 发现走 DHT/PEX，也可由用户配置
  tracker（客户端会把全局默认 tracker 列表附加到每个任务）。任何 BT 客户端都可
  参与 swarm——只有同样运行 BitteChat 的 peer 之间才有聊天。
- v1.0 清单群（应用 v0.4.x"凭空创建"的群聊）与 v1.1 不互通：v0.5+ 客户端不再创建
  此类房间，收到旧清单种子只会被当作普通种子下载。DM 频道机制不变。
- `bc_chat` 为 BEP10 协商扩展：不支持的客户端在扩展握手 `m` 字典中不出现该键，双方回退为纯 BT 行为，互不干扰。
- DHT 条目遵循 BEP44，任何实现了 BEP44 的客户端可读取（验证需要群公钥）。

## 5.1 私聊（DM，v0.6.0 起为 v1.2 机制）

- 频道建立与本地形态见 §1.4；传输帧见 §3.2（m:5-10）。**没有清单种子、没有
  DHT 条目、没有广播**——建立请求只定向发给对方一人。
- 消息密封（与 v1.0 一致）：DM 消息带 `e:1`，`b` 为密封载荷：
  `nonce(12B, = 作者seq小端||0) || ChaCha20-Poly1305(明文)`，
  明文 = `bencode({y:内层类型, b:内层载荷})`，密钥 = `SHA-256("bitte-dm-v1" || X25519(己方seed派生私钥, 对方x) || gid)`。
  外层 `y` 恒为 1，避免泄露消息类型；每条消息携带 `x`（作者 X25519 公钥）。
- **成员校验**：非 dm 双方的消息在 ingest 层直接拒绝；DmReq/DmAccept/DmAck
  的签名必须能被声称的身份公钥验证，且信封 `bc_pk` 与载荷一致。
- **可靠性**：每条 DmMsg 由接收方回签名的 DmAck（m:8）作送达回执；发送方 outbox
  在收到回执前按退避重试。序号缺口（作者 seq 跳跃）触发 DmFetch（m:10）补发；
  peer 重新上线（握手事件）时也自动补发 + 冲刷 outbox。**对方离线时消息保存在
  本地 outbox，待其出现在任一共享房间 swarm 时送达**——DM 不做离线中转
  （这正是"不经 DHT"的代价，也是隐私保证的来源）。
- **在线状态**：对方是否在任一共享房间与我们持有 `bc_chat` 连接（按 `bc_pk`
  聚合），DM 会话页与群列表实时显示。
- 隐私边界：正文、类型、附件名、频道本身的存在对第三方均不可见（没有可观察
  的公共工件）；同 swarm 的其它 peer 至多看到两个节点之间有定向扩展帧往来。
- DM 中的附件仍走附件种子（§2.3）：文件本体需要一个 swarm 传输，但附件消息
  本身经 DmMsg 定向发送。

## 5.2 群名（v0.6.0 起为本地备注）

群名**不是群的公共信息**：显示名 = 本地备注（用户可改）> 种子名（元数据到达时
自动跟随）> 短哈希占位。改名不产生任何网络流量；v1.1 及以前的
`y=3 {st:"rename"}` 系统消息仍会被验证与存储（链完整性），但**不再应用于显示名**。

## 5.2.1 头像（v0.6.0 起仅本地）

身份头像/昵称只保存在本机（identities 表），从不随消息、握手或任何工件广播；
他人的头像由其公钥确定性生成（KeyAvatar）。

## 5.3 消息过滤（显示层，v0.4.3+）

过滤规则（字段 × 模式 × 大小写）**仅在显示层生效**：被屏蔽消息照常验证、存储、
参与 DAG 与头发布（保证哈希链与其他成员一致），UI 将连续被屏蔽消息折叠为
「n 条被屏蔽的消息」，可展开审查。自己的消息永不被自己的规则屏蔽。
